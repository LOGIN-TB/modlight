# Podlight 0.4.0

## New

- **Server mode.** A Podlight server keeps your models reachable for agents while your Mac is off: for n8n, agents on other machines, or a team. It is one container (`ghcr.io/login-tb/podlight-server`) for a VPS, a NAS or Coolify, with its own RunPod key, and runs by the same rules as the Mac: "runs until", idle stop, spending limits checked before a wake, deletion of unused stopped pods, and the safety stop in every pod, which now also covers a server that goes down.
- **Add Server…** pairs the app with a server using the code from its log. Each server gets its own section in the sidebar with its models, Connection, Costs and Server Settings. The overview, the menu bar and the cost figures show the Mac and every server side by side.
- **Access keys.** Agents reach a server with keys of their own, created in the app, one per agent or machine, optionally limited to some models, revocable one by one. The configuration files for OpenCode, pi, Claude Code and Codex are written for the server, with functions named after it (`claude-podlight-office`), so they sit beside the ones for this Mac.
- **HTTPS only.** The app connects to servers over https, except on this Mac and the local network, where it says the connection is unencrypted. The server expects a reverse proxy with a certificate in front of it; Coolify does that when the service has a domain.

## Fixed

- The first request after waking a model could get an empty 404 from RunPod's proxy, which had not started routing to the new pod yet, although the engine already answered. Podlight now waits up to 30 seconds for the proxy instead of passing the 404 on, on the Mac and on the server.

## Under the hood

- The rules both implementations must follow are now one set of 334 cases in `spec/`, including card suggestions, the pod request, hosting and the gateway's error codes, recorded from the Mac app. The Mac app and the server pass the same cases; the server's API is described in `spec/openapi.json`.

## Deutsch

- **Servermodus**: Ein Podlight-Server hält deine Modelle für Agenten erreichbar, auch wenn der Mac aus ist, etwa für n8n, Agenten auf anderen Rechnern oder ein Team. Ein Container (`ghcr.io/login-tb/podlight-server`) für VPS, NAS oder Coolify, mit eigenem RunPod-Key, nach denselben Regeln wie der Mac: „Läuft bis“, Leerlauf-Stopp, Ausgabenlimits vor dem Aufwecken, Löschen ungenutzter Pods und die Notbremse in jedem Pod, die jetzt auch greift, wenn der Server ausfällt.
- **„Server hinzufügen …“** koppelt die App mit dem Code aus dem Log des Servers. Jeder Server hat einen eigenen Abschnitt in der Seitenleiste mit Modellen, Verbindung, Kosten und Server-Einstellungen. Übersicht, Menüleiste und Kosten zeigen Mac und Server nebeneinander.
- **Zugangsschlüssel**: Agenten erreichen einen Server mit eigenen Schlüsseln, die du in der App anlegst, einen pro Agent oder Rechner, auf Wunsch auf einzelne Modelle beschränkt und einzeln widerrufbar. Die Konfigurationen für OpenCode, pi, Claude Code und Codex werden für den Server erzeugt, mit Funktionen nach seinem Namen (`claude-podlight-office`).
- **Nur HTTPS**: Die App verbindet sich mit Servern über https, außer auf diesem Mac und im lokalen Netz, wo sie auf die unverschlüsselte Verbindung hinweist.
- **Behoben:** Die erste Anfrage nach dem Aufwecken bekam manchmal ein leeres 404 von RunPods Proxy, obwohl die Engine schon antwortete. Podlight wartet jetzt bis zu 30 Sekunden auf den Proxy, auf dem Mac und auf dem Server.
